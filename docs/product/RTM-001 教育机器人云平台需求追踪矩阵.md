## 一、追踪规则

### 1. ID 规则

| 对象 | 格式 | 示例 |
|---|---|---|
| 来源断言 | `SRC-<DOC>-<NNN>` | `SRC-03-001` |
| 产品能力 | `CAP-<DOMAIN>` | `CAP-DEV` |
| 产品需求 | `PRD-<DOMAIN>-<NNN>` | `PRD-DEV-001` |
| 用户故事 | `ST-<DOMAIN>-<NNN>` | `ST-DEV-001` |
| 验收标准 | `AC-<DOMAIN>-<NNN>` | `AC-DEV-001` |
| 测试 | `TST-<DOMAIN>-<NNN>` | `TST-DEV-001` |
| 证据 | `EVD-<DOMAIN>-<NNN>` | `EVD-DEV-001` |

已发布 ID 永不复用。需求废弃时保留原行，状态改为 `Deprecated` 并填写替代 ID。

### 2. 状态词汇

| 状态 | 含义 |
|---|---|
| Draft | 需求或映射已编写，尚未批准 |
| Approved | 已由规定 Owner 批准，可以作为开发输入 |
| Implemented | 实现存在，但不代表已验收 |
| Verified | 指定测试通过且证据可解析 |
| Deprecated | 不再适用，保留历史和替代关系 |
| Blocked | 缺少产品决策、设备事实、契约或外部授权 |

### 3. Evidence 规则

- 计划证据位置采用 `docs/gates/evidence/<work-package>/<EVD-ID>/`。
- 真正验收时，Evidence 必须记录 Commit SHA、Schema Version、Artifact/Image Digest、设备组合、测试命令和原始报告。
- 表中的 `Planned` 不是证据；实际文件存在且可复核后才能改为 `Verified`。
- Gate YAML 引用 Evidence ID；不得用会议纪要、演示截图或“CI 全绿”替代具体报告。

### Simulator-only 证据解释

PILOT-001 产生的 Simulator 证据可以覆盖云端协议、状态机、权限、隔离、错误处理和确定性故障场景，但不能单独把以下需求标记为真实产品 `Verified`：PRD-DEV-001 的私钥安全存储、PRD-DEV-006 的真实网络行为、PRD-CNT-005 的设备安装、PRD-AI-003/004 的真实音频与设备互锁、PRD-OTA-002/004 的设备端验签/A-B/断电恢复。

对这些需求应分别记录 `Simulator Verified` 与 `HIL Missing`；只有两类适用证据都满足时，才能将完整 Requirement 标记为 `Verified`。

## 九、变更和审计方法

1. 修改 PRD Requirement 时，同一 PR 必须更新本矩阵对应行。
2. 新增 Story 不得绕过 Requirement；没有产品要求支撑的 Story 视为孤立实现。
3. 新增 Requirement 必须有至少一个有效 Source、Story、Acceptance、Test 和 Planned Evidence。
4. Acceptance 改变行为语义时必须重新评审受影响的 Test、数据契约和 Gate。
5. 实际证据出现后，将 `Planned Evidence` 替换或追加为可解析路径，并记录验证日期和 Digest。
6. 每次 Gate Review 必须检查：孤立 Source、孤立 Requirement、孤立 Story、无测试 Acceptance、失效 Evidence 链接。
